A plugin install, update or removal that Station saved but did not finish applying is no longer reported as a failure. When the runtime pass does not complete, these routes answer `202` with `success: false` and `configurationActivation.status: 'pending'`. `usePluginInstallMutation`, `usePluginUpdateMutation`, `usePluginRemoveMutation`, `requestPluginRegistryInstallAction` (install and uninstall) and `requestRegistryCatalogAction('plugins', …)` used to throw "Install failed", "Update failed" or "Remove failed" for that response. They now resolve with the result. For an install or update the plugin is then not active, and Station does not retry its activation: it stays in Needs recovery until a person recovers it. A removal finishes unloading on Station's next reconciliation. A plugin list read made while the install request is still open reports `installationReadiness: { state: "activating" }`, not `pending`: clients offer no recovery for it until the server reports `pending`. `station plugin install`, `station plugin update`, `station plugin remove` and `station registry install` print the same outcomes.

`@kontourai/station-contracts/plugin` adds `readPluginLifecycleResponse(status, body)` (`applied`, `saved` or `refused`) and `pluginLifecycleUnapplied(body)` (`activation` or `projection`), so every caller reads the response the same way, and `describeActivationDeadline(ms)` for saying the deadline in whole seconds. `PluginInstallResult` gains an optional `configurationActivation` field whose `recovery` (`required` or `none`) and `deadlineMs` say whether the plugin needs recovery and why; readers branch on `recovery` and treat its absence (an older server) as unknown, and `recoverPlugin` reads its response through the same function. A `202` without that marker is still a refusal.
