# Native release operations

The [release process](releasing.md) owns integration, scheduled qualification,
repair sweeps and promotion decisions. This guide owns platform operations.

Station stages every supported package from one immutable `vMAJOR.MINOR.PATCH`
or release-candidate `vMAJOR.MINOR.PATCH-rc.N` tag; Beta `-preview.N` tags are
retired ([#4929](https://github.com/kontourai/station/issues/4929)) and
`Release: Publish` publishes a candidate with `mode=rc` and promotes its
unchanged bytes with `mode=promote`. The tag workflow never publishes the
GitHub Release. It uploads workflow artifacts while each platform builds, then
one assembler creates a draft only after the deterministic inventory and every
checksum validate. `Release: Publish` is a separately approved manual
workflow that downloads and revalidates the draft before making it public. Its
terminal availability job runs only for final publication and has only
`contents:read`, `attestations:read`,
`pull-requests:read`, and `issues:write`: after publication it redownloads and
attests the complete public release again, derives a bounded same-channel
previous-public-release range, and advances only the implicated issue labels.
It has no release, package, or image mutation permission.

The `assemble` and `validate` commands in
[`release-artifacts.mjs`](../../scripts/release-artifacts.mjs) are exercised
as real child processes with the same arguments `release.yml` passes, against
a synthetic asset set ([#2783](https://github.com/kontourai/station/issues/2783)).
That proves the command entry points, not a hosted tagged release.

## Supported inventory

The cross-platform/channel authority is
`config/release-platform-matrix.json`. It declares every development, Nightly,
and Stable cell's artifact, producing job, test lane, signing and
publication requirements, update authority, rollback source, and evidence
selector. `node scripts/release-platform-matrix.mjs` fails when a cell or
workflow job disappears. `--project` resolves current evidence from the deploy
ledger. The projection marks a matching ledger row `VERIFIED`; it does not
independently fetch provider receipts or re-verify their signatures. Its trust
comes from the ledger-writing path. Missing cells remain `NOT_VERIFIED` or
`UNSUPPORTED`; a configured subset is not complete platform delivery.

The [variant owner](../../scripts/lib/release-variants.mjs) and checked-in
[inventory schema](../../schemas/release-artifact-manifest.schema.json)
cover portable server, macOS arm64 and x86_64, Windows x86_64, Linux x86_64,
and Android universal APK/AAB, plus the iOS simulator archive and device IPA.
A final `vX.Y.Z` and a candidate `vX.Y.Z-rc.N` inventory the same variants:
asset names carry the tag (`station-v0.2.0-rc.1-…`), while the inventory's
`version` is the base `X.Y.Z` and its `channel` is `stable`. One parser,
[`release-tag.mjs`](../../scripts/lib/release-tag.mjs), reads the tag for every
staging script and refuses retired `-preview.N` tags
([#4929](https://github.com/kontourai/station/issues/4929)).
Every desktop updater bundle must have its
matching Tauri `.sig` file, and that signature must name the manifest's
version in its trusted comment (`version:`): assembling `latest.json`
(`scripts/lib/tauri-updater-manifest.mjs`) refuses an unversioned or
mismatched one. The macOS archive is signed with `tauri signer sign
--app-version` from the staged app's `CFBundleShortVersionString`; the
desktop app needs the version bound to restore a downloaded update after a
restart. The check reads the comment only; the app verifies the signature. `publish-release`
runs this policy from the default branch, so re-running publication, or a
break-glass pointer repair, for a tag built before this rule (whose macOS
signatures name no version) is refused at "Assemble and validate the rolling
desktop updater channel", before the updater channel is uploaded (the
host-stream manifest attach runs earlier in that job). Rebuilding such a tag signs with its own,
older script, so its updater channel can be published only by a new release. Artifact names are canonicalized by
`scripts/release-artifacts.mjs`; do not rename files in Actions or by hand.

Inventory schema v2 additionally admits exactly four canonical SBOM assets:
`station-sbom-portable.cdx.json`, `station-sbom-desktop.cdx.json`,
`station-sbom-mobile.cdx.json`, and `station-sbom-container.spdx.json`. They
are generated by `scripts/generate-release-sboms.mjs` from canonical npm, Rust,
and container fragments in a separate scratch directory with fixed predicates
(`runtime`, `native`, and `image`). The generator rejects traversal, symlinks, duplicate component IDs,
cross-scope subjects, source/predicate disagreement, non-canonical JSON, and
invalid UTF-8 before the existing inventory authority recomputes the four asset
digests and binds them to the exact release tag; each SBOM names the base
version as its component version.

The production JavaScript fragment now comes from
[`generate-pnpm-sbom.mjs`](../../scripts/generate-pnpm-sbom.mjs), which reads
the authoritative lock graph rather than guessing from installed layout.
`@cyclonedx/cyclonedx-npm` remains pinned to `6.0.1`; `src-desktop/Cargo.toml`
records the matching `cargo-cyclonedx` tool pin `0.5.9`. The container producer
also pins `anchore/sbom-action` at
`66cbf4bc1f1c0d2edc94016e65bc221b6bb0ad6c` and Syft `1.51.0`: after push it
scans `ghcr.io/kontourai/station@sha256:...` (never a mutable tag) as
CycloneDX 1.6 JSON, the version the release validator requires. Its nonempty
package inventory is bound to the recorded image
digest, source SHA, and two-platform descriptor, transferred as a runner
scratch artifact, and converted to the canonical `container/image` fragment.
Scratch source is never admitted to `release-assets` or uploaded to the draft;
only the four canonical SBOM assets can be release assets. Stage creates the
fragments in runner-local scratch, generates and validates the four SBOMs
before it can draft a release, and attests them. Publish redownloads every
asset and rechecks the inventory and exact scope predicates before any image
alias or release-visibility effect.

Draft assembly copies producer files into `release-assets` only from the
explicit artifact allowlist in
[`release-admit-producer-assets.mjs`](../../scripts/release-admit-producer-assets.mjs):
both macOS desktop artifacts, Windows, Linux, portable, the host stream
(`station-host-stream`: the five server archives and the manifest payload),
Android, and the container descriptor, plus, for Stable only, the iOS simulator archive and the
`release-assets/` directory of the staged TestFlight artifact. It refuses a
missing or empty allowlisted artifact, a nested entry, a symlink, and two
producers that emit one file name. Build-provenance descriptors, scanner
scratch, TestFlight receipts, the per-target `station-server-<target>` build
artifacts, and test artifacts in the same download root are never copied. An
unexpected flat file inside an allowlisted artifact is copied here and then
refused by the inventory that runs next. A new producer artifact needs one allowlist entry there.

The simulator archive is deliberately `verification-only` and unsigned. It is
not an installable distribution or a readiness claim. The earlier recorded local probe
compiled and packaged the arm64 simulator app, installed and launched it, and
rendered the branded Station connection UI. A fresh simulator client correctly
shows the connection state until a Station server is configured; this is not a
distribution-readiness claim. The release workflow retains the archive as a
diagnostic/smoke input, not an end-user install channel. That historical
observation was not rerun in this documentation audit. All other variants
marked distributable must satisfy the platform-signing contract for that
operating system. Desktop updater signing is tracked separately: macOS tagged
releases require both a valid platform signature and a Tauri updater signature;
Linux AppImage has no platform-signing mechanism but still requires its updater
signature. Windows always requires its updater signature, but its Authenticode
claim is recorded rather than assumed
([#3591](https://github.com/kontourai/station/issues/3591)): the
`desktop-windows` job stages `station-<tag>-windows-x86_64-signing.json`, an
attested receipt bound to the MSI checksum with `platformSigningState`
`VERIFIED` (a `Valid` signature by the imported certificate) or `NOT_SIGNED`.
The job's PowerShell step only records what `Get-AuthenticodeSignature`
reported; `scripts/lib/windows-release-signing.mjs` decides, and refuses every
other status (`HashMismatch`, `NotTrusted`, `UnknownError`, ...). The inventory's
`windows-x86_64` `platformSigning` claim (`signed`/`platform-signature` or
`unsigned`/`not-applicable`) must match it. Until Windows signing is
provisioned, tagged MSIs ship `NOT_SIGNED`, as Nightly does, and users see the
SmartScreen prompt once; `release-artifacts.mjs draft-notes` derives the draft
signing notice from the inventory and appends it to the generated changelog and installation instructions before creating the draft. The validator rejects false or conflated signing
claims, a Windows claim that differs from its receipt, missing bytes, duplicate
variants, source/tag disagreement, invalid checksums, and missing updater
signatures.

Release Stage invokes the same `npm run build:desktop` wrapper as Windows
Nightly. It supplies the Stable signing and version overlays. The wrapper
appends the generated WiX resource overlay, which uses shallow source paths
while preserving the installed Node dependency layout.

The release tag is also the native application version authority. The root
`package.json` records one stable release-train base (`X.Y.Z`); preflight
requires both `vX.Y.Z-rc.N` and `vX.Y.Z` to match that base, then creates a
release-only Tauri overlay with Stable identity and the bare base version
`X.Y.Z` for both, so a candidate's bytes can later be promoted unchanged.
The overlay also derives Android `versionCode` and iOS `CFBundleVersion` from
the tag (`major * 10_000_000 + minor * 10_000 + patch * 100 + slot`, where
slot is the candidate number 1–98 or `99` for a direct-final build).
Promotion retains the accepted candidate's slot N; it never builds slot 99.
Minor is limited
to 0–999 and patch to 0–99, and a tag outside those bounds is refused, because
an overflowing component would collide with or outrank a later release
(`v0.1.100-rc.1` and `v0.2.0-rc.1` would both be `20001`). That integer is
what Play and App Store Connect use as the monotonic build number; do not
fall back to Gradle's `1` / `1.0` defaults for a store upload. Nightly
Android uses a different application id and its own day-based numbering. Before
each Nightly build starts, the workflow writes an immutable
`nightly-version-code/<code>` Git tag. That append-only reservation ledger means
a failed/retried build cannot reuse a code that might already be installed or
uploaded; scheduled builds automatically choose the next code, and a manual
index is accepted only when it is higher than every existing reservation. The
one pre-ledger published code is a permanent floor in
`scripts/lib/nightly-build-identity.mjs`, so the first ledger-backed run also
cannot regress it.
Desktop, Android, and iOS builds consume the same overlay; the platform jobs
inspect package metadata where the host tooling exposes it before uploading.
Nightly build zero uses `base-nightly.YYYYMMDD`, showing the UTC date. A
same-day rebuild uses `base-nightly.YYYYMMDD.<build>` (where `build` is 1–99), so
the Android and macOS artifacts carry the identical, strictly higher updater
SemVer as well as the shared `day * 100 + build` numeric code. Here `day`
remains whole UTC days since 2020-01-01; the native numeric code and reservation
tags keep their existing allocation. Dated versions sort after legacy
day-counter versions of the same base release. Portable server versions
encode the same allocation as `base-nightly.YYYYMMDDNN`, with a two-digit
build index, to preserve the installer's single numeric prerelease suffix.

## Product version and release cut

The private root package owns Station's product number, initially `0.2.0` for
the first full release train. `scripts/product-version.mjs` synchronizes its
native mirrors. Published CLI and library packages retain their independent
Changesets versions; do not reset them to the product number.

After an immutable RC/final tag is cut, move main to the next development
minor through a normal isolated delivery PR. The existing tag/source remains
frozen. From a clean sibling worktree descended from that source:

```sh
npm run release:cut -- --tag v0.2.0-rc.1
npm run release:cut -- --tag v0.2.0-rc.1 --apply
```

The first command prints the plan without editing. Explicit apply changes only
the root product number and native mirrors to `0.3.0`. It checks clean state,
exact source/head identities, tag/base agreement and source ancestry, and is a
no-op if the base already advanced. It never creates, moves or pushes a tag;
commit and verify the resulting branch through ordinary hooks and review.
Subsequent candidates still use their release train's frozen base, not main's
new development base. Their exact source must continue to satisfy the existing
main-ancestry and qualification guards. The cut helper does not create a
release branch or grant off-main publication authority; this repository has no
automated frozen-train fix procedure. Coordinate such a source through normal
integration while preserving main's next development base.

Nightly publication independently reads bounded public release history and
refuses a root base at or below the highest public RC/final base. A failed or
malformed history query cannot authorize publication, and neither can an empty
listing. A successfully read, non-empty history with no public RC/final permits
initial bootstrap. The guard runs in
the top-level Nightly decision, portable publication and native cohort
admission. Forgetting the cut bump therefore stops publication rather than
shipping a Nightly that orders below the released train. Source tests of this
guard do not prove an installed client's update offer.

## Manually dispatching Nightly

## Native Nightly cohort

`nightly.yml` checks cadence hourly, requires an exact-source usability gate, and
runs the native work as two reusable phases, both only on `refs/heads/main`
when the gated SHA is the workflow event SHA.

Phase one, `nightly-native-stage.yml`, needs the source usability gate: it reserves the cohort
identity, then stages a signed Android AAB (arm64-v8a only, #1456), notarized
macOS downloads, a Windows NSIS installer with a mandatory Tauri updater signature
(Authenticode is optional for Nightly), one shared desktop
manifest, and the signed, audited iOS package (#1454)
as run artifacts with content-bound stage receipts. It performs no product publication: no Play upload, release asset, rolling
tag move, TestFlight upload or deploy-ledger write. It does create the immutable
reservation tag, signed artifacts and attestations, and can submit notarization
requests. A failed stage is not a claim of no external effect or cost. Every staged artifact is attested under this workflow's identity, which
is what the protected verifier checks staged bytes against. Rust dependency
compilation is cached per platform (`Swatinem/rust-cache`, restored on every
ref, saved only from `main`, #1455).

Phase two, `nightly-native-cohort.yml`, needs the exact-SHA source usability gate and phase one, and receives the reserved identity as
inputs. It admits the staged bytes against their stage receipts, creates the
promotion fence, and then publishes **per platform** (#1774): Android (Play
internal), the shared macOS/Windows desktop prerelease, and the already-audited iOS package
(`testflight-delivery.yml` in `delivery: upload` mode, which never rebuilds)
each run from that one admission and fence, in parallel, and none of them
waits on or is withheld by another provider's outcome. The desktop publisher
waits for both desktop builds, verifies their version-specific uploads, then
replaces `latest.json` last. It records separate macOS and Windows claims for
that one provider operation; the two desktop outcomes must agree. The Android
job records its own provider claim — `reported_success` from a provider readback, or `unknown`
with the run reference when its provider step did not succeed — as a
per-platform state artifact. The Play readback
(`scripts/query-google-play-release.mjs`, which the protected verifier also
runs) reads the internal track and bundles through a temporary edit that it
never commits. Each attempt acquires a new access token, creates its own edit
and deletes it. A step that times out, a network failure, a 408, a 429 (after
`Retry-After` when Play sends one) or a 5xx is retried, up to three attempts.
Each step is limited to 15 s, the readback to a 60 s budget, and no attempt
starts with less than 10 s left. An edit cleanup that starts at the deadline
still gets 5 s, so the readback ends within 65 s; the verifier allows it 90 s,
and the workflow step allows 3 minutes. A 400, 403, 404 or other non-retryable
status, an observation the parser rejects, and a cleanup that fails after a
failed read end the readback at once. A cleanup that fails after a good read
is a warning that names the edit: Play invalidates an uncommitted edit when
the same account next creates one. Each failure names the step and the
attempt. Three Nightly runs (43418305981, 43530636495 and 44019513466) went
red because a single 15 s attempt stalled after a successful upload.

The protected verifier (`protected-finalize`) runs whenever at least one of
Android or the shared desktop release published. It joins all three platform
state files into one
verification candidate (a platform that never retained its state is joined as
an explicit `unknown` claim, never inferred), observes the provider of every
platform that reported success — Play track and AAB identity for Android;
release assets, rolling tag, both updater signatures and the shared manifest
for macOS/Windows, plus the attested Windows signing and payload receipt — and
emits the attested final receipt. That receipt's `state` is derived from what
was observed: `complete` when every required platform was verified as
published, `partial` when only a subset was, and its `platforms` map names
each platform `complete` (with its provider), `NOT_VERIFIED`, or
`NOT_PUBLISHED`, the last two with the reason from that platform's own
claim. The distinction is derived from the claim, not chosen: the provider
effect (Play upload; release assets and the `nightly-desktop` tag move)
precedes the claim step, so a job that ran and whose outcome is unresolved
(`unknown`, or no state left behind) is `NOT_VERIFIED` — its build may
already be served — and only a job that never ran (`not_attempted`) is
`NOT_PUBLISHED`. A platform can be `complete` only when the receipt carries
its provider observation, and an unverified platform never carries one. A
partial cohort is a disclosed outcome, not an error the other platform pays
for.

Recording (`record-native-completion`) verifies the final receipt's
attestation, then writes an Android row and a shared desktop row for the
providers the receipt verified as published, with `native cohort final receipt <state>` in the gate
column and, on every row it writes, a note per `NOT_VERIFIED` or
`NOT_PUBLISHED` platform and an `ios:` note carrying the TestFlight job
result (iOS has no ledger channel of its own). The same commit carries the
run's `nightly-npm` row when the CLI receipt from this run verifies; one commit
means one push, so a night disturbs in-flight merge groups once, and
[releasing](releasing.md) describes the fallback that records the npm row
alone. The rolling Android marker `refs/tags/nightly` moves only when the
receipt says Android published; the desktop publisher binds `nightly-desktop` in
its publishing job, before its claim step. The next plan's decide step
(`scripts/nightly-cohort-decide.mjs`, rule in
`scripts/lib/nightly-cohort-decision.mjs`) therefore never treats a marker
at the source SHA as proof of a verified ship: after peeling generated ledger
commits, each platform counts as shipped only when its marker is at the
source SHA **and** the deploy ledger on `origin/main` holds a row for its
channel (`nightly-android`, `nightly-desktop`) at that SHA. The row is the
evidence — it exists only for a platform the receipt verified — so a row
from a `partial` night counts for the platform it names, and a marker at the
source SHA without a row (a macOS claim that failed after the tag moved,
#1780) rebuilds the cohort with the platform and reason in the step summary.
A night that published macOS but not Android leaves `nightly` behind and
rebuilds for the same reason. The ledger is read from `origin/main`, not the
checkout, because rows land on `main` after the ship: the checkout at the
source SHA can never contain the row for its own marker. A missing ref or
malformed ledger fails the plan closed rather than reading as "no rows".
A required TestFlight upload or internal-delivery failure reddens the Nightly
run and opens the `main-health` tracker, but never blocks Android/macOS finality, the ledger, or the marker.
The iOS matrix cell keeps `NOT_VERIFIED` evidence until a processed TestFlight
channel receipt exists (#1016).

Immediately after admission, an annotated, content-bound
`refs/tags/nightly-promotion-fence` is created from the exact plan and
admission, and the Android and macOS publishing jobs revalidate the live
fence immediately before their provider effect (the iOS delivery workflow
does not read it). Planning fails closed on any earlier valid fence: it means
a prior run that had provider effects in flight did not reach its end. The
fence is cleared by the terminal `clear-promotion-fence` job at the end of
every run whose fence job ran — whether that job succeeded or created the
ref and then failed its own readback — whatever the platforms' outcomes: it
re-asserts the exact fence object when the ref exists, deletes it, and
confirms the 404 (a 404 on the first read means no fence was created and
there is nothing to clear). A disclosed partial night therefore never blocks
the next one. Only a cancelled run, or a run whose clear job itself failed,
leaves the fence standing for an owner to inspect and remove; that failure is
disclosed in the recovery receipt's `fence` block.

When any of the Android/macOS publish, finalize, record, or fence-clear jobs
did not succeed, `record-native-recovery` uploads a content-bound
`native-cohort-recovery.json` receipt (`state: incomplete`) disclosing every
job result, each platform's own recorded claim, job result, and derived
state (`REPORTED`, `NOT_VERIFIED`, `NOT_PUBLISHED`), the fence outcome, and
the digests of every evidence file the run left behind. It writes no ref.
`refs/tags/nightly-recovery-lock` is an owner-placed halt only: automation
never creates it, and planning dereferences and validates it
(`assert-recovery-tag-object`) and fails closed while it exists. The
validator requires the tag message to be the receipt's canonical JSON byte
for byte, and `git tag -m` appends a newline, so an owner halting future
Nightlies after an incomplete night creates the tag from a file with
verbatim cleanup:

```sh
node scripts/release-cohort-workflow.mjs canonical-recovery-message native-cohort-recovery.json > lock-message.json
git tag -a --cleanup=verbatim -F lock-message.json nightly-recovery-lock <source sha>
git push origin refs/tags/nightly-recovery-lock
```

and removes the tag explicitly when done; without it, the next Nightly plans
normally.

### When the verifier gets no runner

`protected-finalize` runs on `macos-15` after the providers have published. It
needs macOS for its tools, not for trust: it reads the updater archive's
`Info.plist` with `/usr/bin/plutil` and records `sw_vers` in the receipt.
The trust comes from the protected environment, the hosted runner and the
workflow identity the final receipt is attested under. On the Free plan a
hosted macOS job can wait in a queue and then be cancelled by GitHub with
zero steps and the annotation "The job was not acquired by Runner of type
hosted even after multiple attempts". From 2026-11-02 to 2026-11-16 this
happened to at least 24 macOS jobs in Nightly and iOS build runs, all
between 13:00Z and 21:40Z on weekdays. Two of them were this verifier (runs
42242672641 and 43863134706).

When that happens, `confirm-finalize-runner-loss` reads the run attempt's
jobs API (`scripts/nightly-finalize-runner-loss.mjs`). It reports
`runner_lost=true` only when the verifier concluded `cancelled` with runner
id `0`, no runner name and no steps. In that case
`protected-finalize-retry` runs the same job once more on the same image. A
verifier that ran and failed, timed out or succeeded is never retried, and a
human-cancelled run skips both jobs. Both attempts upload the one
`nightly-cohort-final-<run>` artifact name. `record-native-completion` runs
only when exactly one attempt verified: the first one, or the second after
the first never started. The run stays red because the first attempt shows
as cancelled, but the ledger rows and marker are recorded. The
incomplete-cohort receipt counts a verified second attempt as confirmed
finality. A second runner loss is not retried again.

If no verifier attempt ever ran, the cohort is public without a final
receipt and without ledger rows. The next eligible Nightly treats the source
as a failed delivery and rebuilds every platform under a new identity. To
finalize the published cohort instead, re-run only that run's failed jobs:

```sh
gh run rerun <run-id> --failed --repo kontourai/station
```

This path is only for a run in which no verifier attempt ever got a runner.
If either attempt ran and failed, `--failed` would re-run a real verification
failure; do not use it. Even then it is safe under the workflow's own rules
only when all of these hold:

- No later Nightly has published. The verifier observes the live Play track,
  rolling tag and `latest.json`, so a newer cohort fails it closed.
- It is less than 24 hours after the staged attestations were made. The
  verifier refuses older attestation timestamps.
- Only the cancelled verifier jobs and their dependents re-run. The fence
  job and the publishers succeeded, so they are not re-run. If one were re-run
  without the fence job, it would fail its live fence check before any
  provider write, because the first attempt cleared the fence.
  `record-cli-ledger` and the record job's npm row both use `--if-absent`.

Never use "Re-run all jobs". It re-stages and republishes the cohort. Run
41720227898's attempt 2 (a `--failed` re-run on 2026-11-03) re-ran only the
failed `Build and smoke darwin-x64` job of the reusable portable workflow and
its dependents. Its `Plan the Nightly version`, `Create promotion fence` and
`Verify providers and finalize` jobs were carried over with their original
start times and runner ids, and the re-run jobs downloaded artifacts that
attempt 1 had uploaded. That was observed for the portable workflow in that
run. It has not yet been observed for the cohort workflow's publishers.

macOS staging passes `--overlap-notarization`, so the two `notarytool submit
--wait` waits run concurrently: the Nightly disk image encloses a signed but
not-yet-stapled application, whose own ticket Gatekeeper resolves online, while
the disk image and the updater archive's application both carry stapled
tickets. RC and direct-final releases keep the serial staple-then-package order,
so an application copied out of one of their disk images validates offline.
The macOS packager retries `stapler staple` or `stapler validate` once when
exit 68 carries the specific Apple CloudKit ticket-lookup transport diagnostics.
Missing or invalid tickets, signature failures, timeouts, truncated diagnostics
and a second transport failure remain terminal. Each attempt stays within the
release deadline; notarization acceptance, staple validation and Gatekeeper
assessment remain required before artifact admission.

The independently published CLI remains outside this cohort. The Nightly
Android, macOS, and Windows matrix cells carry `requiredForPromotion: true` and the
`per-platform-native-cohort` availability policy; these are invariants
`scripts/release-platform-matrix.mjs` asserts for those three cells so a matrix
edit cannot silently demote a required platform, not properties the cohort derives at
run time. This is only an available configured subset, and fleet/CLI
completion remains `NOT_VERIFIED`.

## macOS installer disk image

Tagged builds ask Tauri to produce only the application bundle. The release
packager seals that app and owns disk image creation.

Stable RC/final and Nightly disk images open as an installer window: fixed
660×400 icon view, toolbar, sidebar, path bar and status bar hidden, 128-point
icons, the application on the left at (170, 210), and an `Applications` link on
the right at (490, 210) over background art with a drag arrow. The
[packager](../../ops/release/macos-notarized-artifacts.mjs) creates the image
with one `dmgbuild` command (phase `DMG creation`). That command copies the
sealed application with `ditto`, adds the link and background, writes the
window layout into `.DS_Store`, and compresses to UDZO. Finder is never
scripted, because Finder automation is unreliable on hosted runners.
[`dmgbuild-settings.py`](../../ops/release/dmg/dmgbuild-settings.py) owns the
layout. The packager passes `--no-hidpi` so the shipped background stays the
committed two-resolution TIFF byte for byte.

A nonzero `dmgbuild` exit gets the same bounded creation retry `hdiutil` had
(three attempts, 5 s and 15 s backoff). `dmgbuild` drives `hdiutil` internally,
so runner contention still surfaces as that exit. Timeouts, output overflow,
and failures from any other program are never retried. One ten-minute
large-artifact budget covers the copy and the compression. The older
`ditto`-then-`hdiutil` path gave each step its own ten minutes.

After notarization and stapling, the packager mounts the image read-only and
admits the root only if it contains exactly four entries. `.DS_Store` must be a
regular file. `.background.tiff` must be a regular file with the same SHA-256
as the committed `ops/release/dmg/background.tiff`. `Applications` must be a
symbolic link whose target is exactly `/Applications`. The application must be
a real directory. Any extra, missing or differently typed entry fails the
release before the mounted signature, bundle identity and Gatekeeper checks
run. `dmgbuild` ignores the exit status of its internal `ditto` copy, so the
settings file's `create_hook` runs `codesign --verify --deep --strict` on the
copied application inside the still-writable image. A failed or partial copy
makes `dmgbuild` detach the image and exit nonzero before signing or
notarization; the later mounted checks still run.
This check proves the image's structure, not how Finder draws it: window
geometry stays outside its scope. In a mounted image on macOS 26 with the system in
Dark Mode, Finder still painted the application and Applications names
near-black on this background, and Light Mode uses dark names too, so the art
paints a light plate behind each name. Recheck a real Finder window after
changing the art or icon geometry.

To change the art, edit
[`render-background.swift`](../../ops/release/dmg/render-background.swift)
(its geometry must match the settings file), then regenerate and commit the
TIFF:

```sh
out="$(mktemp -d)"
swift ops/release/dmg/render-background.swift "$out"
tiffutil -cathidpicheck "$out/background.png" "$out/background@2x.png" \
  -out ops/release/dmg/background.tiff
```

The mounted check reads the committed TIFF's digest at run time, so a
regenerated background needs no separate pin.

### DMG layout tool supply chain

`dmgbuild` is the repository's only pip-installed tool. It is used only by the
macOS jobs in `release.yml` and `nightly-native-stage.yml`, and is never
shipped or imported by Station. Station has no Python dependency policy or
Dependabot ecosystem for it. The boundary is instead fixed in
[`requirements.txt`](../../ops/release/dmg/requirements.txt): `dmgbuild` and
its two runtime dependencies, `ds-store` and `mac-alias`, at exact versions
with each wheel's SHA-256. A secret-free step before signing creates a venv in
`$RUNNER_TEMP` with the runner's `python3`, refuses Python older than 3.10, and
runs `pip install --require-hashes --only-binary :all: --no-deps`. pip
therefore installs only those three reviewed wheels, never builds an sdist
and never resolves another package. A hash mismatch fails the job. `dmgbuild`
itself then runs inside the signing step, with that step's environment and
unlocked keychain, so the pinned wheel digests are the integrity control.
Upgrading means reviewing the new wheels and replacing the versions and hashes
together. Nothing re-pins automatically.

## Prebuilt portable server qualification

[`portable-server-archives.yml`](../../.github/workflows/portable-server-archives.yml)
is a separate build/smoke matrix for platform-specific server archives. The
[builder](../../scripts/lib/portable-server-archive.mjs) stages the selected
Node runtime, native dependencies, compiled server/UI/CLI, and platform launcher.
It also stages the bundled Station catalog and its declared local packages,
including the curated engineering Skills, from tracked source files. The archive
smoke starts a fresh server and checks that the catalog resolves the collection
inside that extracted archive. Listing it does not install it or grant tools.
It refuses a target that differs from the build host's platform and architecture,
because native dependencies come from that host's install.
It marks the tree as prebuilt so the CLI does not try to rebuild it at startup.
The workflow's smoke checks that archive through an isolated long-path home,
without relying on a host Node executable. A declared matrix is not a current
pass or published release.

The workflow also builds and embeds the source-bound telemetry companion at
`telemetry-companion/`. Its required smoke checks the extracted payload's
inventory, digests and source SHA before launching the server. The existing
signed archive authenticates those bytes without another signing key. The
payload remains `build-only`: server archive qualification does not qualify
companion installation, containers, credentials, storage recovery or telemetry
delivery. See the [companion boundary](../../deployment/telemetry/README.md#artifact-and-private-files).

The platform-array release manifest now selects these archives through
`install.sh`'s explicit signed-public-manifest path. The installer verifies the
host target, launcher protocol, signed size/hash and release identity, stages
the bundled runtime under `versions/<version>`, then promotes the active link.
When a running Station service's fixed launcher runs that install, the installer only
stages the version and the launcher trials the switch instead.
It does not run dependencies or build that archive. The Windows zip is
`install.ps1`'s, which installs it the same way without a service
(#2675 slice W2; a Windows service is not switched yet). The default authenticated
GitHub path and schema-v1 public source manifests still install and build a source
release under `releases/`. See the [consumer formats](../../packaging/manifest/README.md#formats-and-consumers)
and [installation lifecycle](release-channel-ports.md) for prerequisites,
upgrade and rollback behavior. Fixture signing and archive smoke results do not
establish production publication, key custody or a user's installed outcome.

## Nightly fleet staging

`nightly-fleet-staging.yml` is an independent reusable, portable-only evidence
lane. It is not a native-promotion dependency. Its Actions artifacts are
staging receipts, not a GitHub release, updater feed, Play upload, TestFlight
build, container registry image, or Linux package-repository publication.

The final `nightly-fleet-staged-inventory-*` artifact content-binds every
portable variant to the source SHA, workflow run, static-plan digest, build
check/SBOM evidence, artifact bytes, and GitHub attestation verification. It
does not stage container, Windows, Linux, or iOS variants: those remain gated
and `NOT_VERIFIED`. No staged portable artifact proves availability, an
install, or an update; those outcomes remain `NOT_PUBLISHED`, `NOT_INSTALLED`,
and `NOT_UPDATED` in the admitted inventory.

Normal operation is an independent scheduled Nightly with an hourly cadence
decision, a six-hour default minimum publication interval and its serialized
delivery lease. It checks cadence before expensive source tests or builds.
Manual dispatch remains available for recovery. Both entry points require the
same exact-source lint/typecheck/native-boundary/browser-smoke gate and retain
signing, inventory, attestation and provider admission. They use their workflow event SHA,
never stage a source their published markers already contain, and skip
native staging only when the
cohort decision has the required platform markers and matching ledger rows.
The tag alone is insufficient, as described above. To request that normal behavior
manually, leave the optional field empty:

```sh
gh workflow run nightly.yml --repo kontourai/station --ref main
```

`source_sha` is retained only for callers that echo the current workflow event
SHA. Nightly rejects an older revision explicitly, rather than letting native
or CLI publication silently fan out from an obsolete checkout.

`rebuild_index` is only for an exceptional same-day rebuild of a commit that
was already built. It is an integer from `0` through `99`, never a boolean;
the immutable reservation ledger still rejects a reused or regressing code.
For example, after confirming that index `7` is an unused safe index for the
current UTC day:

```sh
gh workflow run nightly.yml --repo kontourai/station --ref main -f rebuild_index=7
```

The workflow validates the optional index before reserving the physical build
host, so inputs such as `true`, negative values, or values above `99` fail
without consuming scarce capacity.

## Linux AppImage runtime layout

The Linux desktop overlay normally puts the bundled Station server, seed data,
schemas, and Node dependencies under `usr/lib/Station`. That layout remains
the `.deb` and `.rpm` contract. AppImage is deliberately different: linuxdeploy
walks `usr/lib` and invokes `ldd` while constructing its AppDir, which is not
safe for the staged vendor executables in the Node dependency tree.

The release job therefore builds `.deb` and `.rpm` first with the ordinary
`tauri.linux.conf.json` resource layout. It then invokes Tauri again for only
the AppImage with `tauri.linux-appimage.conf.json`. The merge overlay moves
the server, Node dependencies, examples, and schemas to `usr/share/Station`
and enables the Rust `appimage-runtime` feature. The
[native host](../../src-desktop/src/lib.rs) resolves that runtime relative to
the executable in the same AppDir. The registry bridge, desktop sidecar,
and tray build label use this path. The packaging check extracts the AppImage
and verifies the resource layout and build identity. A working startup still
requires a launch on Linux.

The staged server and `node_modules` are adjacent for ordinary Node module
resolution once the correct entrypoint is selected. Desktop releases also ship
the pinned `station-node` executable through Tauri's `externalBin`; `.deb` and
`.rpm` place it under `usr/bin/station-node`, without claiming `/usr/bin/node`.
The host uses the executable beside its own binary and preserves the user's
PATH. See [packaged runtime](desktop-build.md#packaged-runtime) for the pinned
archive, license and separate macOS Node signature. The
[staging helper](../../scripts/lib/desktop-server-runtime.mjs)
refuses missing or over-budget runtime inputs. That is packaging evidence,
not proof that the current AppImage can start or execute a staged Agent.

Tauri constructs and signs the final AppImage and then produces the updater
archive and signature. Station deliberately selects Tauri's `v1Compatible`
updater mode because the cross-platform release inventory is archive-based
(`.app.tar.gz`, `.msi.zip`, and `.AppImage.tar.gz`, each with its signature).
Changing that mode requires migrating the workflow, inventory schema,
cryptographic validator, tests, and documentation together. Do not extract,
patch, repack, or otherwise mutate an AppImage after that signing step. Correct
the source overlay or the staging contract and create a new build instead.

### Smaller desktop updates

`v1Compatible` selects legacy archive formats, not binary delta generation.
The pinned Tauri CLI schema offers that string or a boolean, with no delta
mode. The updater downloads and signature-verifies a complete artifact before
installing it. Switching to `true` can change Windows/Linux container formats;
it does not make unchanged runtime files disappear from the transfer.
The authority remains
[`native-release-config.mjs`](../../scripts/lib/native-release-config.mjs).

A delta design needs release-owner approval of both the producer and client
contract: identify the exact installed base by digest, produce per-base patches,
authenticate the patch and reconstructed target, bound reconstruction disk and
memory, preserve platform signatures, and fall back to the full signed artifact
for an unknown, modified or unavailable base. Qualification must exercise
interrupted downloads, corrupt patches, withdrawn targets, restart recovery,
upgrade and rollback on each supported platform. The release inventory/schema,
asset naming, feed, validators, provenance and retention must change together;
existing clients still need their full archives during migration. No updater
mode, asset contract, feed, signature or publication behavior changes here.

Until then, pruning unused runtime distributions reduces full downloads while
retaining the existing release contract. See the
[Claude executable trade-off](desktop-build.md#claude-executable-trade-off)
for why the large offline fallback stays bundled.

do not enable Tauri's updater artifacts and therefore do not produce an updater

An optional local updater-generation check must use a disposable test key and

secret. The public key is injected into a release-only Tauri overlay; updater generation is

which release workflows run after initialization. The tracked Gradle seed is
not the only authority: channel workflows can recreate the project. Reapply
and test that helper instead of assuming Tauri will never replace the file.
macOS Developer ID
signing and API-key notarization data
(`APPLE_DEVELOPER_ID_CERTIFICATE_BASE64`,
`APPLE_DEVELOPER_ID_CERTIFICATE_PASSWORD`,
`APPLE_DEVELOPER_ID_SIGNING_IDENTITY`, `APPLE_API_KEY_ID`,

with both set it must verify as `Valid`, signed by that certificate. Setting only one, or setting
`WINDOWS_SIGN_COMMAND` (which only Nightly implements so far), fails the job.
Each protected platform job checks only its own credentials before it starts
its signing operation. There is no shared credential-aggregator job and no

the optional Windows pair remains required and fails closed. See [mobile-release.md](./mobile-release.md) for the trust
configuration and store-side first-run steps. Never commit certificate,

configured, Android APK/AAB signatures, and Tauri updater signatures before

## Stage, inspect, publish, and roll back

App Store review may outlast publication on other platforms. An enabled App
Store-action feed retains its previous payload until authenticated readback
confirms the exact RC build is released. The
[held-feed procedure](https://github.com/kontourai/station/blob/main/docs/guides/store-entry.md#app-store-review-and-a-held-update-feed)
uses `repair_app_store_feed_only` after manual release; the existing desktop
pointer repair flag keeps its original scope.


Push an immutable RC or direct-final tag only after an authorized release
handoff. `Release: Stage` binds it to one source SHA, and hosted full regression
must pass on that exact source before a producer can build, sign or upload.
Container staging uses an immutable candidate-specific tag,
`ghcr.io/kontourai/station:staging-<producer-tag>`, so another RC at the same
qualified source does not overwrite the first. The draft is created only after
platform delivery, inventory, checksums and advisory checks succeed. Inspect
`station-release-inventory.json`, `station-release-checksums.txt`,
`station-release-store-authority.json` and `station-container-release.json`.
Every platform payload is attested by its producer; inventory and checksums are
separately attested roots because they cannot hash each other.

Dispatch `Release: Publish` on main through `native-release-publish`:
`mode=rc` publishes the candidate prerelease without moving Stable authorities;
`mode=promote` takes that public RC and creates the final tag/release from its
unchanged bytes; `mode=stable` publishes a separately built direct-final draft.
All normal modes re-admit exact-source qualification and a fresh advisory audit.
The source checkout supplies content, a pinned default-branch policy checkout
supplies release policy, and the workflow event commit supplies the publication
receipt's certificate source. These SHAs are retained separately.

Promotion authenticates the RC assets against `release.yml` at the producer ref
and source digest, verifies the exact transfer plan, and attests
`station-release-promotion.json` using `publish-release.yml` at its recorded
workflow SHA. RC names, inventory and SBOMs remain unchanged; the final release
adds transfer lineage instead of pretending those assets were rebuilt under a
final tag. The immutable final ref is created with the workflow credential so
it does not trigger another producer. A pre-existing destination is refused
unless an explicit repair authenticates its completed publication receipt.
Attempted GitHub and store effects are journaled before mutation and retained
as run artifacts. After interruption or a lost response, inspect the unknown
outcome and actual provider state rather than repeating the operation blindly.

Promotion first plans and then applies exact-build store operations. Configure a
dedicated Play identity through `GCP_PLAY_PROMOTION_WORKLOAD_IDENTITY_PROVIDER`
and `GCP_PLAY_PROMOTION_SERVICE_ACCOUNT`, restricted to this repository's
main-branch `publish-release.yml` identity and protected publication environment.
It needs the intended production-track authority for Stable, not Android upload
key access. Preserve the separate tag-scoped Stage WIF trust. The publication
environment also needs `APPLE_API_KEY_ID`, `APPLE_API_ISSUER_ID` and
`APPLE_API_PRIVATE_KEY`. These declarations do not establish live IAM or secret
configuration. See [store entry](store-entry.md#same-build-production-promotion)
for first-launch and listing requirements.

For final publication the workflow verifies the candidate-specific staging image
against the container descriptor, then promotes only `image@recorded-digest` to
Stable aliases. RC publication skips aliases, mobile feeds, rolling desktop/host
pointers, deploy-ledger writes and availability projection. The repository-wide
publish lock serializes public authority changes.

Final publication requires the public `stable-desktop` rolling release to exist.
Bootstrap it once with signed-in owner credentials:

```sh
gh release create stable-desktop --title stable-desktop --notes "Rolling desktop updater channel."
```

A workflow `GITHUB_TOKEN` must not create this workflow-crossing ref. Leave the
new release public and empty, then explicitly set
`allow_empty_updater_channel_bootstrap` for its first final publish. A non-empty
rolling release missing `latest.json` is damage and fails closed. First-release
issue projection additionally requires `allow_empty_availability_baseline`;
a successful no-prior-release result writes no issue labels, while unavailable
or ambiguous history still fails. A failed draft takes a new immutable tag,
never replacement assets under a reused tag.

The draft also carries the host stream: the five `station-server-*` archives
and `station-server-manifest-payload.json`, attested by release.yml. Publish
checks the payload against the tag and the archive bytes and dry-run signs it
on every run. The producer-attestation loop skips
`station-portable-<ring>-manifest.json`, which Publish attaches and verifies
against the pinned release key and attested payload instead of a release.yml
attestation. A promoted release also carries `station-release-promotion.json`;
its separate publish-release.yml attestation and digest-bound lineage are
verified before the unchanged producer assets. Behind `STATION_PORTABLE_RELEASE_PUBLISH`, publish signs
the manifest and attaches it before publication. For final publication the
separate `host-pointer` job then moves `portable-stable`; RC publication attaches a signed versioned
manifest when enabled but never moves that pointer. It runs once publish reports
the release public, even if the deploy ledger later fails, and its own
failure never skips the ledger or release availability. It takes the signed
manifest from the public versioned release and verifies it with the pinned
key before any pointer write. It re-verifies the public
versioned assets and replaces only a strictly older pointer, restoring it if
the re-verification fails. It only re-verifies when the pointer already
serves this run's bytes, and it leaves the pointer alone for an older tag,
such as a desktop rollback. A rerun that finds the manifest already attached
to the release compares its bytes and never replaces it. Details and the
owner actions are in
[signed host-stream manifests](release-rings.md#signed-host-stream-manifests).

Stable RC and final desktop builds embed the Stable rolling endpoint. An RC
therefore uses Stable identity; acceptance testing must reinstall later RCs
manually because they share the same base version.
The default branch's policy checkout runs the updater manifest assembly and
remote channel verification scripts before and after rolling asset changes.
The target tag's release-artifact validation still verifies the updater archive
signatures against the release-bound public key before publication. Publish
uploads the signed updater archives to the rolling release before replacing
`latest.json`, then redownloads and verifies the complete result. The pointer
guard refuses to replace a newer manifest with an older version, so a delayed
draft cannot silently regress the channel. On failed remote verification, the
workflow attempts to restore the prior `latest.json` (or remove the first
bootstrap pointer). That compensation reports command failure but does not
perform a second remote readback of the restored pointer. Inspect the channel
after a failed publish rather than assuming compensation completed.

Rolling release assets require owner-managed retention because every publish
adds eight versioned archives and signatures. Before a publish, record the
version named by the current `latest.json`. After the publish and remote
verification succeed, retain `latest.json`, all eight assets for its current
version, and all eight assets for that recorded previous version; delete only
assets from older versions with `gh release delete-asset`. Never prune the
previous version before the next publish: pointer compensation can restore its
manifest, which must continue to resolve to those archives. Apply this procedure
to `stable-desktop`, and verify every asset URL
in the retained current and previous manifests before completing the sweep.
The locally installed GitHub CLI 2.97.0 help documents the `assets` JSON field
but does not document whether `gh release view --json assets` imposes a result
cap, so that availability concern remains unconfirmed; a missing `latest.json`
still fails closed before the publish job is scheduled.

The normal recovery for a bad desktop release is a higher fixed version. If an
owner must stop offering the bad version before that replacement is ready, use
the protected `allow_published_pointer_repair` and
`allow_updater_pointer_regression` dispatch inputs only after
reviewing the candidate tag, the current rolling `latest.json`, and the target
channel. This break-glass permits the older pointer and is recorded in the
workflow dispatch. For a direct-final build select `mode=stable` and its
published final tag. For a promoted build select `mode=promote` and its original
published RC tag, retaining the completed final transfer receipt for
authentication. With both flags set, an admitted published source is
accepted for pointer repair: the workflow revalidates its signed assets,
updates only the rolling desktop archives and `latest.json`, and skips the
store promotion, container aliases, mobile feed and deploy-ledger publication. Tauri will not
downgrade clients that already installed the newer version; those clients still
require a higher fixed release. After the repair, verify the rolling release's
archives and `latest.json`, then leave the guard enabled only for that single
dispatch.

To withdraw a bad public desktop build, first repair its rolling channel:
dispatch this workflow with the last known-good source and matching mode above, with
both `allow_published_pointer_repair` and `allow_updater_pointer_regression`
enabled, then verify that
`stable-desktop` serves the intended version's matching archives,
signatures, and `latest.json`. Confirm the computed source, authenticated
promotion lineage when applicable, and rolling target before approval.
Changing only the bad tag release
back to a draft does not repair the independent rolling release and must never be
treated as desktop rollback. After the rolling pointer is repaired, remove the bad tag
from installer resolution by changing it back to a draft, revoke any affected
external-store listing, and publish a higher replacement version. Already
updated Tauri clients cannot downgrade and still require that higher fixed
release. Container aliases are convenience pointers, not rollback evidence:
recover by retagging the exact prior `image@sha256:...` recorded in its public
release descriptor, and verify the alias resolves to that digest. Never rebuild
a rollback image or infer its digest from a mutable alias. The immutable GHCR
`staging-<producer-tag>` tag is retained for forensic review and must never
be overwritten.

For a promoted release, retain its original RC release and assets as public
objects while referenced by the signed host payload. Re-drafting or deleting
that RC breaks the promoted host downloads even if the final copies still
exist. Withdrawing visibility alone also does not undo Play production or an
App Store review submission; inspect and recover each provider separately.
