Getting Started

Run Station on your computer and connect an agent such as Claude Code or Codex. This guide covers installation, your first chat and Project, connecting a phone, and keeping Station updated. To share a Project with someone, read the sharing setup and current limits.

Quickstart

  1. Install Nightly on the computer that will run Station. Open the app or use the single-use sign-in link printed by the installer.
  2. On Home, open the Agent control beside Start and choose an Agent that is ready. If Home offers Set up an agent engine, use that action to open Connections. For an existing Codex account, follow First chat with Codex.
  3. Try a small request such as “Give me three questions to check before I review a documentation change. Use no tools.” Choose Start to open a direct chat.
  4. Read the answer in the chat. If an approval or question appears, inspect it before responding. When the answer has a Basis chip, open it to inspect the recorded inputs behind that answer.
  5. Keep talking in the same chat, create a Project for shared context, or track a deliverable in a Task. Choose what fits.

How a turn works

                    ↓
The selected Agent runs one turn in a Session
                    ↓

                    ↓

A follow-up can add another turn to the same Session. See the visual walkthroughs for Gallery captures of the interface. The Learn Station atlas explains how the parts fit together.

First chat with Codex

If Codex is installed and signed in on this computer, you can use that account without adding a model API key:

  1. Start Station using one of the paths below. For a source checkout, follow the README commands and open the single-use sign-in link printed by ./station start.
  2. Open Customize (the sparkle icon at the bottom of the sidebar) → Connections → Engines → Codex. Confirm the account is signed in. Check connection sends a short message using your model allowance.
  3. An empty Home guides you through choosing an agent and optionally adding files. View available agents opens the agent list; Set up an agent engine opens Connections when no agent is runnable. On Home, open the Agent/model control beside Start. Choose Agent, then Codex, write a request, and choose Start. You can start without a Project. The detected Codex Agent is enough; creating a custom Agent is optional.
  4. Choose New Project on Home. Blank workspace creates an empty Station-managed directory when your workspace mode allows it. Choose From a repository to acquire a Git checkout or, on the Station host, choose Use an existing folder to reuse one. For Git acquisition, open Start from a Git repository. Choose Git URL to paste an HTTPS or SSH URL, or use the GitHub or GitLab tile to browse with a signed-in account on the Station host. Choose Acquire repository, then Use this checkout. Station suggests a name until you edit it. Creation rechecks the acquisition and retains its source and exact commit. Station recommends Coding when the folder is a Git workspace. Choose Create to open the Project, then add documents or connected tools in Files & connections. Operator setup is saved across reloads. Reopen New Project to continue the same creation and starter. See repository setup and recovery and document import. From a chat draft, open its Project picker and choose Create project. Enter a name for a blank Project or choose what to start with. Station selects the created Project and keeps the draft ready to send.
  5. To talk to the built-in Station Assistant using the same Codex account, open Settings → General → Built-in agent engine → Change…, choose Codex, choose Use this engine, then Save. Open the Agent/model control beside Start or Send. Under Agent, select Station Assistant. Ask it to list your projects to exercise a read-only Station tool as well as chat.

For a customized Codex Agent, open Customize → Agents → New agent → Use a connected engine, enter a name, select Codex, and choose its model and Project. In Tools, choose Station to add read-only controls; expand the row to inspect the selection. Save with Create agent, then choose it in a new chat. Codex receives your instructions with the first message in each new chat, at the same priority as that message. (With the Station orchestration instructions Feature Preview on, an Agent that has Station controls also gets Station's own guidance on using them in that first message.) You can edit or clear them before saving. See the Agents guide for tool selection and approval details.

In Coding, use Files to open a project file, Diff to inspect changes, and Terminal for a shell. These controls sit in the right-hand rail. Chat and its inbox remain available alongside them. A successful answer to a file question and a successful Station tool call establish different capabilities; check both before relying on the Agent for work.

If Terminal loses its connection, it keeps its output visible and offers Reconnect terminal. Commands typed while disconnected are not sent or replayed. Reconnecting can reattach a retained shell; restarting Station may end that process and open a new shell with the same tab identity. On a phone, the terminal also offers Ctrl+C, Tab, and command-history arrows.

New installations start without importing conversations outside your Projects. To include those later, turn on Conversations outside projects in Settings. Existing installations retain their choice and previously imported history.

Inspect what a chat used

Choose ⋯ then Chat inventory in the chat header. Pick a group, then View details on an item to read the authored message, attachment metadata, or recorded tool result. Recorded origin identifies the Session, turn and event; Open session opens the surrounding work. Output rows keep their Inspect output action. Items that cannot be read show an unavailable state rather than an empty result. The answer's Basis chip still opens inspection scoped to that answer.

To see how much of the model's context window a chat has used, read the meter beside Send under the message box, or choose ⋯ then Conversation stats in the phone chat header, which names the share used. Either opens the chat's stats.

MCP app previews in chat

In Station's web client, a completed MCP call can show its declared app directly below the tool row. No layout pin is needed. The integration must still be connected and permit rendering, and its current tool definition must declare a UI resource. Station's own inventory and Basis Apps use shipped resources and can mount when Codex owns the default Agent without a Station-engine connection. Inventory App data publication is currently unavailable; frame mounting does not change that limitation. The result itself needs only the standard MCP content envelope. Reloading and opening the saved conversation mounts its retained preview again; Station does not call the tool or start a disconnected third-party server to display it.

App membership is cached for five minutes. New declarations may wait for a stale query to refetch on mount or focus; reload to refresh the catalog. Read-only paired devices may discover and view previews.

The Codex adapter preserves complete MCP results with canonical server/tool identity. Claude-provider MCP calls cannot mount: their output is summarized to text and their flattened names lack unambiguous server identity. ACP and managed engines have not been qualified. Ordinary calls keep their rows and batching. Sample and offline views outside the connected workspace keep ordinary rows without app lookup. Unknown or disconnected integrations add no app card. Result UI metadata alone cannot mount an app or authorize a resource read.

The preview follows your theme and labels interactions as unavailable. App tool calls, resource reads, messages and links are refused in transcript previews. Fullscreen and model-context notes are not supported there yet. Native shells continue to refuse scripted MCP frames; use the web client for these previews. See the host design for the capability boundary and remaining work.

Connect your phone

Your computer runs Station and the agents. Your phone connects to it to read replies, continue chats, and review work. Start on your computer:

  1. Install and launch Station there using the options below.
  2. Open the Station name at the top of the computer’s window and choose Pair phone. Station opens straight to a pairing code on a reachable HTTPS address, and lists any other HTTPS addresses to switch to. Settings → Pairing → Pair device opens the same screen. Any of your own paired devices with full access can do this, not only the computer. On a phone the same choice reads Connect another device. If your organization's policy allows only this computer to connect, these are turned off and say so.
  3. On a new phone, open Station and choose Scan pairing QR code. Scan the invitation from the computer. Enter a pairing code is available if the camera cannot be used. Keep the computer running.

Scanning a pairing code on the phone needs a reachable HTTPS address, such as the computer's Tailscale HTTPS address, which Station lists first when it is configured. Both devices still need access to that address.

For local network access, enable Settings → Pairing → Discover this Station nearby on the computer, then choose Find nearby Stations on the native phone app (on the welcome screen it is under More ways to connect). Discovery is off by default and shows names and local addresses without granting access. Select the intended computer, confirm the exact address and any unencrypted HTTP warning, request access, and approve on the computer. Android versions before Android 14 offer QR and manual address entry instead. Browser clients do not browse the local network. Choose Enter Station address to type an address when discovery is unavailable or finds nothing.

If an exchange loses its response or cannot save approved access, Station holds the attempt instead of sending the one-time proof again. Choose Pair again to send a fresh request; approving it replaces any access the held attempt left behind, so you don't need to revoke anything on the computer first. For a pairing code, create a new code on the computer.

A new phone shows the connection welcome until you save a real Station. A saved Station that is offline or needs access keeps its connection recovery controls instead. The welcome does not run workspace queries against an unconfigured endpoint.

Station's phone apps are not in public app stores yet. Android builds reach testers in a Google Play internal testing group and iOS builds reach invited TestFlight testers. Without one of those, open the Station's reachable address (see below) in your phone's browser instead; the browser offers the same Pair with a code step and Request access.

A browser opened with the host's one-time sign-in link can create invitations and manage paired devices. Choose Read-only, Standard or Full device access before creating the invitation; anyone holding it can pair once before it expires, without another approval. Cancel an unused invitation to prevent it being redeemed. Revoking a paired device removes access it already received.

For a terminal-only host, run station-nightly environment offer on the computer running your Nightly install (or ./station environment offer from a source checkout). This prints a single-use invitation with Standard access. Use --scope=orchestration:read for read-only access or --require-approval to review the recipient before granting access.

A browser that arrives without an invitation can choose Request access. Approve that request in a trusted session or with the displayed command on the Station host. Bare host-approval commands discover the running Station in the selected local home before consulting saved Station defaults, so a saved remote Station does not override that local instance. Use the same home and channel that started Station; a remote host requires running the command there, such as over SSH.

The address in that invitation must be reachable from your phone. localhost means the device you are using, so a computer’s localhost address does not reach it from a physical phone. Use the reachable address shown in the pairing flow; see Connections for remote access. A pairing code grants access; it does not create a network route.

If you have no Station yet, install and open it on your computer using the options below. The phone's connection manager offers QR scanning, pairing-code entry and Connect a Station for a host address. Broker route setup is a separate advanced option. You can start with an ordinary chat; custom Agents, remote tasks, and layouts are optional.

Preferences across devices

Open Settings → General → Your account to set the approval default for your new Codex, Claude or Muse chats. You can also use the chat's approval picker and choose Save as my … default. Full access requires an explicit confirmation. An Agent's own default takes precedence over your personal preference; an explicit chat choice takes precedence over both. Existing chats and unattended jobs keep their settings. Device grants and Station policy still control what may execute.

Appearance, chat display, answer delivery, diff preferences and model-picker choices follow the same signed-in person across devices connected to this Station. They are saved as you change them, and other clients refresh on focus or reconnect. Import previous preferences brings over this browser's older portable choices without replacing settings your account already has. Use default removes a personal display choice; choosing Default for a new-chat approval mode returns it to the Agent, Station or engine setting.

While offline, changes wait on this page and are not saved yet. Keep the page open until saving finishes. If another device changed a composite preference, Reload saved preferences shows the current choice before you try again.

Microphone/output providers, push permission, haptics, keyboard behavior and shortcuts, screen layout and device access stay on the device. Settings labels which scope owns a choice. If your Device is not linked to a person, preferences remain local. Different Stations keep separate account preferences.

The approval chip shows the known mode, including Full access, Auto or Ask. Default means the engine's own settings apply and its active mode has not been confirmed. For Codex, inherited settings resolve to a supported mode when the reported approval policy and sandbox match. Otherwise, the picker describes the engine default as your own Codex settings. If you set none, no command Codex runs uses the network or writes outside the chat's folder and temporary directories without asking; it may ask before other writes too. Codex's web search and MCP tools are not commands and are not covered by this. Open the picker to see the source, the confirmed mode and whether a request takes effect next turn or requires restarting the session. A Claude chat started in a chosen mode by someone who may grant full access can switch to full access on its next turn. A chat left on Claude's own settings, or one that started before this was available, gets full access on its next turn too: Station relaunches Claude Code first and resumes the same conversation. A chat that is waiting on you or still running background work, or one on a Station running as root outside a sandbox, needs a restart.

Read recent conversations offline

In the browser, open Settings › Privacy & sharing and enable Save offline reading copies. It starts off. Then open conversations while connected to save text from their most recent history read: at most 20 conversations, 10 recent turns per conversation, 256 KiB per conversation and 2 MiB in total. Copies expire after 24 hours or a build change. Tools, reasoning, attachments and provider recovery state are excluded. A running answer is captured after its history is read again; this is not a continuous backup.

Message text can contain pasted secrets. These local IndexedDB copies have no additional encryption, and anyone using this browser profile can read them while offline. Enable this only on a device where that trade-off is acceptable. Clear offline copies deletes the saved text and turns saving off. Signing out, changing credential authority or account, or switching Station also clears the copies. A build change also turns saving off with the expired copies, so enable it again after an update. Reachability failures leave saved copies and the saving preference intact.

A browser reload while the Station route is unavailable shows a separate, read-only reader with a Read-only copy saved timestamp. If you lose connectivity in an already open workspace, choose Read saved copies; Back to workspace keeps drafts and the existing outbox available. Reconnecting leaves the reader, verifies live access and uses server data. Local copies never enter the live transcript or authorize actions.

After one successful web-worker installation on HTTPS or localhost, the app shell can load offline. An initial visit without any cached shell still needs a network connection. Only the local text reader bypasses live access verification; ordinary protected query caches remain quarantined on a cold offline start. A small identifier-only session index is persisted under the normal 24-hour, build and authority rules, rather than caching provider recovery state or titles taken from prompts. Native shells already bundle their app assets; the browser service-worker cache is not installed there.

Station is open source and under active development. Check the release list for current artifacts. Desktop updater channel tags and npm packages are separate from the signed portable release rings used by the installer below.

Install Nightly

Nightly is built from main and published as signed prebuilt server archives. On macOS or Linux:


curl -fsSL https://raw.githubusercontent.com/kontourai/station/main/install.sh | STATION_CHANNEL=nightly sh

On Windows, in PowerShell:


$env:STATION_CHANNEL = 'nightly'; irm https://raw.githubusercontent.com/kontourai/station/main/install.ps1 | iex

STATION_CHANNEL=nightly is enough: the installer reads the rolling portable-nightly manifest, verifies its Ed25519 signature against the keys pinned in the script, and checks the size and SHA-256 of the archive it selects for this host. Nothing unsigned is installed. It needs curl and tar on macOS and Linux; with no Node.js 24 on the host it downloads a pinned, digest-checked Node.js only to verify and extract. Neither a GitHub login nor a build is needed.

The install lives under ~/.station/installs/nightly, keeps its data in ~/.station/instances/nightly, and owns the station-nightly launcher (~/.local/bin/station-nightly, or station-nightly.cmd on Windows). Open the single-use sign-in link printed when it finishes. For later launches on macOS/Linux, use one command:


~/.local/bin/station-nightly start

On Windows, in PowerShell:


& "$env:USERPROFILE\.local\bin\station-nightly.cmd" start

The default browser address is http://localhost:38000; use the sign-in link when access is requested. Run the same install command again to upgrade. Replace start with --version in the launch command to see the installed build. Set STATION_INSTALL_PUBLIC_MANIFEST_URL to install from a different signed manifest instead. The Station Nightly desktop app uses the same ports and data directory; the installer refuses to share them silently (see channel identity and coexistence).

Each Nightly's own install.sh and install.ps1 are also attached to its immutable v<version> release, next to its archives.

Nightly desktop downloads

Each Nightly desktop publication also uploads its installers under fixed names, so these links normally serve the newest published build (each replacement deletes the old file first, so a download at that moment, or after a failed upload until the next build, can briefly find nothing):

  • macOS (Apple silicon): https://github.com/kontourai/station/releases/download/nightly-desktop/station-nightly-macos-aarch64.dmg
  • Windows (x64): https://github.com/kontourai/station/releases/download/nightly-desktop/station-nightly-windows-x86_64-setup.exe

The release also carries the same builds under versioned names (station-<version>-…), and versioned downloads of earlier builds; older ones may be removed once 30 newer builds have been published. Its SHA256SUMS lists the newest build's downloads under both names. Download it next to the installer and check it, for example shasum -a 256 --ignore-missing -c SHA256SUMS on macOS, sha256sum --ignore-missing -c SHA256SUMS on Linux, or compare (Get-FileHash <file>).Hash on Windows. A mismatch right after a new build is published means the two files are from different builds; download both again.

The Windows installer is not publisher-signed yet (#3591). This applies to the Nightly installer and to the Windows MSI on tagged releases (station-v<version>-windows-x86_64.msi), whose release records it as unsigned. When you run the downloaded installer, Microsoft Defender SmartScreen therefore shows "Windows protected your PC" with an unknown publisher; choose More info, then Run anyway. On Windows 11 with Smart App Control turned on, Windows can block the unsigned installer with no such option. The app's own updates are verified with Station's updater signing key.

Before You Install

You need:

  • Node.js 24.x
  • npm 10 or newer
  • git, curl, and tar
  • GitHub CLI authenticated with gh auth login

Authentication is used for GitHub release metadata and attestation checks. There is no unsigned fallback.

Optional, Linux only: a C++ toolchain (g++, make, python3) to compile the node-pty native module that powers interactive terminal panes. macOS and Windows use shipped prebuilds. Without a toolchain on Linux, Station still installs and runs, but terminal panes are unavailable and station doctor reports the degraded terminal capability with the remediation (npm run dependencies:install after installing the toolchain, then restart — that runs the reviewed lifecycle path, unlike a direct npm rebuild). Agent execution does not use node-pty and works either way.

Install Or Upgrade


sh -c 'set -eu; file=$(mktemp "${TMPDIR:-/tmp}/station-install.XXXXXX"); trap '\''rm -f "$file"'\'' EXIT HUP INT TERM; curl -fsSL https://raw.githubusercontent.com/kontourai/station/main/install.sh >"$file"; chmod 600 "$file"; GH_TOKEN=$(gh auth token) sh "$file"'

For an available signed release, the installer verifies its GitHub OIDC attestation and SHA-256 receipt before it builds and starts Station. The stable channel installs under ~/.station/installs/stable, writes runtime data to ~/.station/instances/stable, and owns the station launcher in ~/.local/bin. Open http://localhost:18000 after the command completes.

Stable and Nightly are the supported distribution channels. The installer refuses the retired STATION_CHANNEL=beta and STATION_CHANNEL=preview values. An operator accepting a release candidate can pin STATION_VERSION=vX.Y.Z-rc.N; it installs with Stable identity and the base product version. Follow the release-candidate procedure for acceptance and manual candidate replacement.

An operator can instead supply STATION_INSTALL_PUBLIC_MANIFEST_URL for a signed platform-v2 prebuilt archive. That macOS/Linux path uses bundled Node.js without building Station on the host; it may download a pinned Node.js to verify the first install. It requires a published manifest for the requested channel. See the archive install guide for this separate path and its upgrade and service limits.

Choose A Model Connection Or Engine

Two kinds of connection can power an agent. A Model connection is a local or hosted model service that Station's own engine runs inference on. An Engine is an installed agent CLI, or a custom engine you connected, that runs its own agent loop.

  1. Open Customize → Connections.
  2. On the Models tab choose a detected service or Add model connection; on the Engines tab choose a detected engine or Add engine. During first run, a detected Engine can be ticked to connect it and create its External agent in the same confirmed action. An engine that is starting for the first time can be reported as still starting rather than failed: its Agent is added if it connects while Station is running; otherwise set it up again later.
  3. Follow its setup action until it reports Ready.

For OpenAI's model service, supply its API key. A custom server may use another supported authentication method or need no key. Create saves a Model connection and checks it immediately; if its model list is unavailable, the check may send a small, potentially billable test prompt using the default model. Correct a refused check before expecting the connection to run work.

Read the accompanying evidence too. A saved connection or a live model catalog does not prove that a chat turn completed. An explicit one-turn smoke supplies that narrower proof and can incur provider charges; opening Connections or New Chat does not run it.

For a credential-free first path, use a supported local model service and then return to Connections. Startup can register detected Claude Code, Codex, and Muse engines and their default Agents; with the copilot-sdk-engine Feature Preview on, it also registers GitHub Copilot (SDK) when copilot is on PATH, from the next start. An engine you explicitly removed is not automatically added again. Registration does not prove that the engine is signed in or ready. The discovery screen also offers other local suggestions that you can choose to configure. The Connections guide lists current integrations and their exact setup steps.

Choose the simplest path for what you want to do:

You want to…Start with…
Keep inference on this machineA local Model connection and a Station agent
Use an existing agent engineA supported Engine and its External agent
Use a hosted model through StationA hosted Model connection and a Station agent

Start Your First Chat

Home and the chat dock use the same start composer. On Home it sits under What would you like to do?. New chat opens it in the chat dock as a draft, like an empty chat: the dock opens if it was collapsed, a quiet line names where the chat will start (for example Start a chat in Pulse on studio-mac) until you write something, and the composer sits where a reply would. Write what you want done and choose Start. You do not need to choose anything first; the controls show what Start will use:

  • The combined Agent & model button shows the Agent's icon and the Model's name, followed by the thinking effort when you chose one (for example Opus · High). It opens Agent & model. Its Agent choice lists Station, Coding apps, and My agents, with readiness and setup actions. Its Model choice opens the Engine & model picker, which also offers alternative engines when they are available. An engine choice overrides this conversation's execution while retaining the selected Agent's profile and saved defaults. Search or filter by provider, Recent, or Favorites. Supported thinking effort and Speed controls sit beside the list; on phones, open Settings. Choosing a Model for an Agent also chooses that Agent and closes the picker; changing the effort leaves it open. Once you have chosen a Model, the picker's reset button names the default it returns to, such as Use project default for a model-only choice or Use Agent defaults for an engine override. In an existing conversation, changing or resetting the engine opens a short handoff picker that switches now: your draft, or a catch-up request when there is none, is the first message. Full access, a pending or refused approval change, and a conversation override add a warning glyph to the combined button; open Agent & model to see the same glyph on the choice that raised it. When the conversation's Agent now points at another engine, the button adds Default differs. The panel names the session engine and the Agent default. If the conversation's engine session has already ended, a Next turn starts on … line above the message box says where the next turn goes instead. In the model picker, while a reply you sent is still running, the other engines and Use Agent defaults are shown but unavailable until it finishes. When Station reports that the conversation can't be changed right now (it is read-only, still loading, the check failed, or it is waiting on a turn the server reports as still running), the other engines are not listed and Use Agent defaults is unavailable.
  • The project control in the start heading shows its name, or Without a project. Open it to choose a project. Each project shows its Git repository, or without one the folder its chats run in. For a linked checkout, that is its resolved execution root. An unavailable location states why Station cannot start there; a folder not checked yet is marked Not checked and the start checks it. A project with no folder can be chosen too. Its chats run in your home folder, or, for an ACP engine, in that engine's own Working Directory or else a private folder Station makes for the chat; the chip and list say which. A Codex chat in Codex's sandbox never runs in your home folder: it gets a private folder.
  • A chat Without a project runs in a private folder Station makes for that chat, not in your whole home folder. On Windows, new chat folders live under ~/.station-workspaces/<Station home hash>/; other platforms keep them inside Station's data folder. Windows workspace files need their own backup and retention policy; a Station home archive does not include them. To run such chats in your home folder instead, set Settings › Agent runs › Chats without a project to Home folder (a sandboxed Codex chat still gets a private folder). The setting applies to new chats; a chat that already ran keeps its folder.
  • ⋯ holds Use a visual skill while the Visual skills Feature Preview is on; with it off there is no ⋯.

The start heading includes a clickable Project name. Or start without a project clears it. Home and New Chat use the same composer and pickers; Runs on <Station> sits below the message box.

When another Station is available, Runs on <Station> opens Where this work runs. Choose the Station, then its Engine & model. A Station that cannot take work right now is greyed out with its reason, such as Recovering · server down or restarting or Unreachable. With Paired Station chats enabled in Settings → Advanced → Feature previews, choose a Project from that Station’s own list, or start without a project. Start opens a chat tab that reads and replies to the conversation on the chosen Station. It looks like any chat, with Via <Station> in the header. Replies, files, Stop and approval answers use that Station. A refused message offers Retry and Edit. If delivery is uncertain, use Check before sending a changed copy. Station keeps the original pending message.

To move a chat you already have to a paired Station, open the Agent picker in Agent & model and choose that Station; the dialog becomes Continue elsewhere. Pick its engine and one of its Projects, then Continue on <Station>. A new chat opens there, and its Agent gets this chat's messages as context. The new chat shows messages from the handoff on; this chat keeps the earlier ones. Its first message is your draft or a short catch-up request. Files are not copied: the picker lists uncommitted changes and unpushed commits that stay on this machine, so commit and push first if you need them. The original chat stays here. If Station can't confirm the move, Retry safely reuses the same request and never creates a second chat. A Station you added with a device sign-in can't take a chat: pair it as a Station in Connections first.

Full access, choosing a folder, mentions, offline copies and local skill or workspace integrations are unavailable on a relayed chat. Turning the preview off keeps saved text and drafts visible. An older held chat offers Reconnect chat; confirm the Station before continuing.

Choose the destination’s Project explicitly; Station does not match Projects between computers by name. Remote Tasks keep their separate execution consent.

With that preview off, or for SSH destinations, Start opens Run on a Station and Run task starts a resumable Task there. Its existing portable Project admission still applies. A foreground chat stays on its owning Station; choosing another destination starts new work. With no other Station to choose, the control is plain text.

The Project page opens on Overview. Room is shared discussion with people in that Project, in named channels starting with #general; choose the channel name to switch, and people who can edit can add, rename or archive channels. React to a message with an emoji, and tap a reaction to add or take back yours. You can edit or delete your own messages (press ↑ in an empty composer to edit your last one); a deleted message leaves "Message deleted" so replies still make sense. Use Bring an Agent for an explicit request whose answer returns to the channel. With the Coordinator in #general preview on, the Agent you ask in #general answers, proposes Tasks you start from a card, or passes your message to a running Task, and posts each Task's result back (Coordinator in #general). Direct Agent conversations stay in the chat dock. Tasks shows a board of what each Task needs now, or a list of current work, backlog and history; Files & connections holds the Project's context. To change where new Agent work starts, open the workspace controls under Files & connections. A local folder is execution configuration rather than the Project's identity.

The Project conversation list shows its channels and Task rooms. If one of those lists is temporarily unavailable, retry that list from the Project page.

A Project channel keeps a file for as long as its message stands. If a Project channel pauses attachments while its file store is repaired, it says so; remove the files and your text still sends.

An existing chat can become a Task through New Task from this in its More menu. The Add to Task picker also offers New Task from this for an answer or input. New Task from this starts shaping immediately; type any focus or refinement as your next message. New Task mode stays on through clarifying questions and reloads until you accept a proposal or choose Stop shaping this Task in the chat’s More menu. No Task is created until acceptance.

To keep one chat as your personal agent, turn on Coordinator chat in Settings → Advanced → Feature previews, then choose Make this Houston in the chat's More menu. Home then pins it with Talk to Houston, and Station tells it when your work needs you, fails or finishes. See Houston.

On a Project's Tasks board, a GitHub issue offers Start Task. It copies the issue's description and latest comments into a new Task and links back to the issue; if the issue already has an open Task, Station opens that Task instead.

After reload, an accepted card offers Open Task. The Task description is the Goal sentence. Its shared Task document keeps the complete accepted brief. If saving that document fails after creation, the proposal shows a recovery error: retry Create Task to finish saving the same Task.

The Task opens as a chat room. Press Enter to send, or Shift+Enter for a new line; on a phone keyboard, Return adds a line and the round send button sends. An unsent draft is kept for each room and thread in this tab. Messages from one person within a few minutes share one name and avatar, a divider marks each day, and agents have square avatars where people have round ones. New messages follow the newest message while you are at the bottom; if you scroll up, the room keeps your place, marks where new messages start, and N new messages returns you to the latest. Load earlier messages appears above the visible history. A Project channel keeps the latest 500 messages in view: at that point it says so instead of offering more, and when new messages unload older ones, a note says so above Load earlier messages. A failed agent request stays in the room with Retry and Open run. The Brief is shared with agent requests unless you turn off Brief attached. Saved answers appear in Results, with their source and evidence available through Answer details. For engines that can resume, idle agent threads remain available after restarting Station. Ended or replaced runs still require a new agent request.

Create Tasks from a Project; Home no longer offers a first-task card. Existing guided starter links keep their focused title entry and dispatch receipt. If the Agent is unavailable, Station shows the setup reason without creating a Task. If a start has an uncertain outcome, inspect that Task rather than creating another to retry it.

When a Session reports a plan (ACP engines do), its row in the inbox and on Home, and the Tasks board card and Project task row of a Task it runs, show Agent plan 3/5 and a thin bar. It is the agent's newest plan in that Session's latest turn, refreshed every few seconds while the Session is running or needs you, or while the Task is in progress or blocked. Stopped follows the count when the turn was stopped or the Session failed or was canceled with steps open, and Waiting when the Session needs input or an approval. There is no bar without a plan, for a plan from an earlier turn, on Drafts, on Home's one-line Earlier rows, on rows from another Station, or on done and canceled Tasks. The count is agent-reported: it never marks a Task done or satisfies a gate.

Task status alone does not establish that work passed a gate. Read the run and review evidence. The Starter Work guide explains how Station preserves the same work identity through retries and response loss.

Read Child Conversations

Choose Open chat on a subagent card or a background task to read its transcript in the chat pane, laid out like any chat: the subagent's prompt, then its tool calls and answers. The title becomes Parent chat / Subagent; choose an ancestor to return to that chat without losing its draft or reading position. Escape returns one level. On a phone, the title names the subagent; use the back button or swipe from the left edge. The reader opens on the latest messages; earlier ones load as you scroll up. Engine transcripts are read only and refresh while running.

If a tool result has no recorded text, the reader says Text output unavailable. This does not mean the tool produced no output.

Use Home or the inbox to find work. Notification and session links open that session in Chat, including attached records and sessions whose Agent was deleted. Older Activity links still work: a session link opens its reader, and a collection link opens the inbox. There is no separate Activity page or Quick review pane. Action operations are under Developer → Monitoring, linked from Settings → Advanced → Developer tools.

See Conversations Started Outside Station

The inbox also lists Claude Code, Codex, Grok and OpenCode conversations you ran in a terminal or another app on this machine. Station reads them; it never controls them. These conversations do not raise Station sounds, popups, desktop notifications or mobile alerts, and do not appear on mobile activity cards. A new conversation you continue in Station has its ordinary alerts. Station looks in four places:

  • Claude Code transcripts under projects in CLAUDE_CONFIG_DIR, or ~/.claude when that is not set.
  • Codex sessions under sessions in CODEX_HOME, or ~/.codex when that is not set, and in every other Codex home Station itself runs Codex in: the Codex connection's config home, its Station app home, and each credential profile's home. Continuing a conversation runs Codex in the home it was found in, with that home's account and, for a profile, its settings. A conversation copied by hand into two of them is listed once per copy, since the copies can go on separately.
  • Grok Build sessions under sessions in GROK_HOME, or ~/.grok when that is not set. A Grok session appears once it has a prompt. A subagent's own session is not listed separately, and neither is a Grok chat you started in Station, which is already there.
  • OpenCode's session database, opencode.db or opencode-<channel>.db (for example opencode-stable.db), in opencode under XDG_DATA_HOME, or ~/.local/share/opencode when that is not set. Station reads both OpenCode 1.x and OpenCode 2.x databases. Beside an OpenCode 2.x database, an opencode-next.db is read only for sessions OpenCode 2.x does not hold: a session it copied is shown as OpenCode 2.x has it, archived or deleted there included. Once OpenCode's upgrade has finished, only sessions created in opencode-next.db after it are listed from that file, since OpenCode copies it only once. A file in the OpenCode preview format, which Station cannot read, is skipped. Station opens each database read-only and lists top-level OpenCode sessions you have sent a message in; subagent sessions and archived sessions are left out. A message appears once OpenCode has finished writing it. Later messages wait for an unfinished OpenCode compaction; if one is still unfinished after 15 minutes (OpenCode stopped partway and the conversation was not reopened), Station logs one warning naming the conversation, once per Station run. Conversations Station itself runs through an OpenCode connection are not listed a second time. Older OpenCode releases kept sessions as JSON files under storage; Station does not read those, and current OpenCode moves them into the database when it starts. If an OpenCode update changes the database layout, Station stops reading it and logs one warning instead of guessing. A conversation Station already listed from an OpenCode 1.x database stops updating once OpenCode 2.x converts that database; its earlier messages stay in history.

With STATION_EXTERNAL_ACP_SESSIONS=1 set before Station starts, the inbox also lists the sessions an ACP engine you added under Connections reports itself, for an engine that offers a session list (Antigravity, Factory Droid, Hermes and Cursor do; Kiro does not). This is off by default. Station asks for the list when it checks the engine, about every five minutes, so it starts no extra engine process, and a new session can take that long to appear. Only the session's folder and Project are shown: ACP's one way to read a session's messages also resumes it inside the engine, so Station does not read them, and these sessions cannot be continued in Station. Grok and OpenCode sessions are read from their own stores as above, not from this list, and Station's own sessions and capability checks are left out.

STATION_EXTERNAL_CLAUDE_SOURCE_ROOT, STATION_EXTERNAL_CODEX_SOURCE_ROOT, STATION_EXTERNAL_GROK_SOURCE_ROOT and STATION_EXTERNAL_OPENCODE_SOURCE_ROOT point Station at a different folder (for OpenCode, the folder holding the database). With STATION_EXTERNAL_CODEX_SOURCE_ROOT set, that folder is the only Codex home Station reads. Station checks every two seconds and reads the 128 most recently changed conversations from each place (each Codex home is its own place, up to 512 Codex conversations in all, the default home first). Older ones stay in history once Station has read them, but new messages in them are not picked up until they are among the 128 again. Conversations Station has not listed before appear only after it finishes restoring its own sessions at startup; if that restore fails, already listed conversations keep updating but new ones wait until Station restarts.

Each conversation is filed under a Project by the folder it ran in:

  1. A Project whose folder contains that folder. When two Projects share the folder, the inbox names both rather than picking one.
  2. Otherwise, a Project whose folder is in the same git repository. Every worktree of the repository counts, so a conversation in ../station-worktrees/fix-login or another tool's worktree folder files under the Project on the main checkout. A Project on a subfolder of the repository takes that same subfolder in every worktree.
  3. Otherwise, No project. These conversations have no Project assignment.

Rows can show Directory · …/parent/folder when a working folder is recorded without a Project label. The label provides folder context and leaves Project membership unchanged. A reopened delegated chat can show CLI (reported) when Station's accepted start receipt records a CLI caller.

A conversation keeps its Project after its worktree is removed. If its Project is deleted while other Projects remain, it moves to No project. A conversation inside a git submodule of a worktree outside the Project folder also lands in No project: Station follows the submodule's own .git, which belongs to a different repository.

If a conversation ran in a folder on a network drive that has stopped responding, Station can't tell which Project it belongs to. A conversation Station has already filed keeps its Project. A new one is listed under No project, and Station tries the folder again about once a minute. Once the drive responds, the conversation moves to its Project.

Station copies what it reads into its own history and search index, so a conversation stays in history and in search after the original transcript is gone. You can open these conversations, and so can every device you have paired with session read access, including a phone.

To stop reading conversations from folders outside your Projects, turn off Conversations outside projects in Settings → Advanced (under Host options), then Save (attachedSessionsOutsideProjects in the Station configuration). Station stops on its next check, including for conversations it already lists: new messages in them no longer arrive. What it already read stays in history, in search and readable from your paired devices; turning the setting off removes nothing. Conversations inside a Project are read either way.

A hosted Station never reads conversations outside your Projects. It reads the ones inside a Project, but no account can open them there.

Continue an Attached Session

Open an attached terminal Session from the inbox. It reads like any chat. To continue it in Station, press Continue in Station next to where it says it started; no message is needed. If you typed one, it is sent there once the continuation opens, and pressing Send continues the same way. Claude and Codex create independent child Sessions; the original terminal Session can keep running.

If the conversation is still mid-turn in its terminal, Station says Still running in Claude Code. Continuing now forks it instead of continuing. Mid-turn means its latest turn has not finished and Station saw it written in the last five minutes: for Claude Code, its transcript or a subagent's (while the conversation's own transcript changed in the last two hours); for Codex, the latest record Station imported. A single command that runs silently for longer than five minutes is not seen as running. Choose Not now and continue once it finishes, or Continue anyway to fork it now. A fork does not see anything the terminal Session writes afterwards. Station cannot stop the terminal Session for you. To hand the conversation over completely, finish or quit it in the terminal first. OpenCode and Grok conversations are read only: the message box shows why it is unavailable. Codex continues from the latest completed turn Station has observed, so wait for one if the message box is unavailable.

The continuation starts in the folder the conversation ran in. Its actual confinement depends on the Session's access grant and the engine's enforcement; a continuation granted Full access can run with host authority. The working folder alone is not a sandbox guarantee. Station checks the folder again when you continue:

  • A conversation filed under a Project continues under that Project. This includes one in a worktree outside the Project folder: it continues in that worktree. Station refuses if the worktree was removed or replaced, or if its .git does not lead back to the Project's repository.
  • A conversation under No project continues as a No project chat in its own folder, after you confirm that choice. Its access grant still determines confinement as described above. This is allowed only for a folder inside your home folder. Station refuses your home folder itself, every folder outside it (system folders included), any hidden folder directly in your home folder and everything in it (such as .ssh, .aws or .config), Library on macOS and AppData on Windows, the system temporary folder, and Station's own data folder. It also refuses when the folder shown reaches another folder through a symbolic link inside your home folder. To continue such a conversation, add a Project for that folder or its repository: Add a project for this folder instead in the confirmation opens New project with the folder already chosen. Station does not move a conversation into another Project's folder, because its history refers to files in the folder it ran in.

A hosted Station does not continue conversations outside your Projects.

An attached Session remains read only. Continuing opens a Station-owned child. If Station cannot confirm the result, use the offered retry for that same operation. Engine and configuration problems appear with their setup reason. A continuation receipt confirms admission, not completion of the work.

The continuation runs as the engine's own Agent on this Station, the one New Chat sets up for Claude Code or Codex. That is what lets it open as a chat in the dock and take your next messages there. Those messages keep working in the conversation's own folder, including a folder inside the Project or a worktree, never the Project folder instead. If Station has no Agent for that engine, the continuation is still created and you continue it from Chat; the dock says why it cannot open it.

When Something Goes Wrong

An access refusal names the Station to reconnect to or says it did not accept the message. Your draft stays editable. Check is for an unanswered send; a refusal does not mean delivery is uncertain. Unknown technical errors use a short recovery message, with diagnostics in Details where available.

The session reader and coding tabs use the same reply controls as the dock. Shared Task history keeps the records already loaded when an earlier page fails; use Retry to read that page again. Inbox search, snooze, dismissal and Undo work across its desktop and mobile layouts.

Open the help menu and choose Troubleshoot with an agent, or search the command palette for Troubleshoot an issue. It is also under Settings → Diagnostics.

Where Station shows an error, a Troubleshoot action starts the same conversation with that error already attached:

  • a view that stopped working (under More actions when Station refused the view), and an error notification;
  • a pane that is temporarily unavailable, and a layout tab Station can't show (when Station could not read its installed plugins, the tab offers Retry instead);
  • an engine that isn't connected, and an agent that can't run;
  • a local Station that stopped or failed when Restart Station isn't offered;
  • a reply that failed (Troubleshoot this);
  • a reply you rated thumbs-down, through This looks like a Station bug. Your rating is saved as usual; the bug report isn't added to it.

The assistant receives the page you were on (without anything after ? or #), the error's code and first line with known credential shapes, links and file paths removed, and for a reply, the conversation and turn ids. It never receives a stack trace. Troubleshooting runs on the Station you are connected to; when the conversation isn't stored there, for example one that ran on a paired Station, the assistant is told so and asks which Station ran it, since this Station's logs and diagnostics don't cover it.

  1. Describe what went wrong in your own words and choose Start troubleshooting. You can paste or drop screenshots into the chat.
  2. The Station Assistant asks for the steps that reproduce the problem and which app and build you saw it in, then investigates with Station's own tools.
  3. It offers to fix the problem, file it, both, or neither. A fix changes configuration only through Station's approval prompts, after you agree. It will not restart the Station it runs in; it gives you the steps instead.
  4. To file, it shows the complete redacted report first and waits for your yes. It posts the issue itself only when you are the Station owner and this computer's GitHub CLI can label issues in kontourai/station. Otherwise it gives you a prefilled link to submit as yourself.

These are instructions the assistant follows, not checks Station enforces. Read the report before you approve it.

The assistant can't read Station's server logs unless the Station owner grants it access. If it asks, copy the relevant lines from Developer → Logs, or download the diagnostics bundle from Settings → Diagnostics and paste the parts that matter. Logs can contain conversation content.

If the Station Assistant has no engine, these entries open Report a problem instead. The design covers the details.

From a terminal

If the app itself won't open, run station triage in a terminal. It collects bounded, redacted diagnostics into a private run folder, then starts Codex or Claude, whichever is installed, as a troubleshooting conversation that follows the same playbook. The agent keeps its usual approval prompts, so it asks before it runs a command. It works from the run folder, Station's log folder and commands such as station doctor, because Station may be down. It will not stop or restart anything unless you say yes. To file, it prepares the report with station triage draft-report, shows you the redacted text and waits for your yes, then posts it or gives you a prefilled link.

Use station triage --headless for a read-only, one-shot diagnosis that saves diagnosis.md and issue-draft.md instead. That is also what happens when input or output is not a terminal. station triage --context-only collects the diagnostics without starting an agent. See the CLI reference.

Update, Stop, Or Uninstall

Recovery boundaries

Use the recovery path that owns the thing you need to recover. The bundled client's station triage gathers bounded, read-only artifacts; it cannot run a local source doctor. Run ./station doctor from a checkout (or portable release) for host diagnostics. Installer rollback concerns a released program candidate; station home backup and station home restore concern one inactive runtime home and retain the replaced home. They are not interchangeable.

Run the installer again in the same channel to update safely in place. To stop and start the stable local Station manually:


station stop
station start

To uninstall the stable program while preserving Projects, connections, Tasks, and Sessions:


STATION_CHANNEL=stable "${STATION_ROOT:-$HOME/.station}/installs/stable/current/install.sh" uninstall

For Nightly, use that install's retained installer:


STATION_CHANNEL=nightly "${STATION_ROOT:-$HOME/.station}/installs/nightly/current/install.sh" uninstall

Add --purge-data only when you also intend to delete the selected channel's home (~/.station/instances/stable or ~/.station/instances/nightly). The installer accepts purge only for a data root it created and marked; it preserves an unmarked pre-existing directory for manual review.
